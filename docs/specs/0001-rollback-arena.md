# 方案：确定性回滚对战（暂名 rollback-arena）

> 状态：**已定稿**（2026-10-15，决策见文末）。开新会话，从这份文件开始实施，第一步是 S0。

## 目标

做一个**能在浏览器里联机对战的 1v1 3D 小游戏**，网络同步用确定性模拟加回滚（GGPO 那一类做法）。它同时要满足两件事：

1. **有技术难度、拿得出手**：定点数学、确定性模拟、回滚和重模拟、状态快照、网络条件模拟、去同步（desync）检测，每一项都是 Unity 客户端面试能深挖的点。
2. **展示 AI Coding 工作流**：整个项目按 `ai-workflow` 的流程做，并且把「AI 怎么验证一个它看不到、也没法凭感觉判断的系统」做成项目最主要的亮点。每个阶段都如实记录 AI 做了什么、我做了什么、花了多少时间和钱。

**交付物**：
- itch.io（或个人站点）上能直接玩的 WebGL 版本，两个浏览器窗口就能对战；
- 公开的仓库；
- 一个带调试叠加层的演示，能看到回滚次数、重模拟了多少帧、校验和；
- 一份带数据的开发复盘。

## 不做

- 匹配、账号、大厅（用房间码加中继就够了）；
- 3 人以上对战、观战（观战列为可选的延伸）；
- 服务器权威和反作弊；
- 精致美术：用基础几何体或低多边形，统一风格；
- 移动端、手柄以外的平台适配；
- 用 Unity 自带的物理系统做游戏逻辑（它不保证跨平台确定性）。

## 背景与成熟做法

| 参考 | 是什么 | 怎么用 |
| --- | --- | --- |
| **GGPO** | 格斗游戏回滚网络同步的事实标准（C/C++，MIT）。游戏侧只提供三件事：保存状态、读取状态、给定输入推进一帧；输入交换、预测、回滚调度、时间同步由库负责 | **照它的模型设计**，不直接用（只支持 Windows，接 Unity 成本高） |
| **GGRS**（Rust 版 GGPO） | 把回调改成「请求列表」；提供 **SyncTest**：每帧都回滚 n 帧重模拟，比对校验和，不联网就能在本地查出不确定性 | 照搬 SyncTest 和请求列表的思路 |
| **Backdash**（C#） | 受 GGPO 启发的 C# 回滚库，目标框架 .NET 8，beta | 作为参考实现；Unity 兼容性没确认，不作为依赖 |
| **FixedMathSharp / UnityFixedPointMath** | Q32.32 定点数库，有平方根、三角函数 | 作为自己实现的**对照基准**，必要时退而使用 |
| **Photon Quantum** | 商业的确定性预测回滚引擎 | 证明这条路在商业上走得通；不用，因为会把技术核心藏起来 |
| Netcode for GameObjects / Entities | Unity 官方方案，服务器权威 + 预测，不是确定性回滚 | 不用，属于另一种模型 |

关键事实：
- 浮点数在不同 CPU、编译器（Mono、IL2CPP、WebAssembly）下结果可能不同，所以回滚游戏普遍用定点数。Burst 的跨平台浮点确定性目前搁置了，不能指望它。
- 去同步的常见来源：浮点数、没有固定种子的随机数、依赖真实时间、依赖容器的遍历顺序。
- Unity WebGL 不能用 UDP，只能用 WebSocket 或 WebRTC。

## 设计

### 游戏

**1v1 平台擂台**：两名角色站在一块悬空的平台上，能移动、冲刺、跳跃，有一个攻击。攻击有起手、生效、收招的帧数据；命中后有击退，把对手打出平台就赢一局，三局两胜。

选它的原因：
- 节奏快，对延迟敏感，回滚的价值看得见；
- 规则少，状态小（每名角色几十个字段）；
- 帧数据让「第几帧命中」可以写成精确的测试。

模拟以 60 Hz 固定步长运行。玩法在 XZ 平面上，Y 轴只管跳跃和掉落；碰撞只用竖直胶囊体（XZ 平面上是圆）加平台边界。画面用 3D 呈现。

### 架构

```text
Arena.Sim          纯 C#，不引用 UnityEngine，不准出现 float/double
  Fixed64 (Q32.32)、FixVector3、确定性随机数、三角函数查找表
  GameState：全是值类型、定长数组，可整块复制（为了快速保存和读取）
  Step(ref state, inputs) → 下一帧；Checksum(state)
Arena.Rollback     纯 C#
  RollbackSession：输入队列、预测、回滚、重模拟、输入延迟、时间同步
  SyncTestSession：每帧强制回滚 k 帧，比对校验和
  ITransport：消息收发接口
Arena.Net
  SimulatedTransport：同一进程内模拟延迟、抖动、丢包、乱序（有固定种子）
  WebSocketTransport + 一个很小的中继服务器（.NET 控制台程序）
Arena.Unity        表现层
  按模拟状态渲染；回滚纠正时做视觉平滑；调试叠加层；回放
tools/headless     dotnet 命令行：机器人对机器人、浸泡测试、回放、哈希日志
```

和 HeirCut 一样，纯逻辑层与引擎分开：模拟和回滚都能在 `dotnet test` 里离线跑成千上万次。

**考虑过但没选的方案**：
- **锁步（lockstep）**：更简单，但所有输入都要等对方，延迟一直存在。不过回滚框架里把输入延迟调大、关闭预测，就是锁步，可以顺带演示两者的对比。
- **服务器权威 + 客户端预测**：这是另一套模型，也更重；而且对 1v1 格斗类来说，回滚是业界的主流做法。
- **直接用 Backdash 或 Photon Quantum**：技术核心就变成别人的了，失去作品集的意义。

## 验证设计（项目的核心亮点）

| 编号 | 检查 | 怎么做 | 能抓到什么 |
| --- | --- | --- | --- |
| V1 | 定点运算正确 | 随机生成百万组用例，与 `BigInteger` 参考实现比对；溢出行为写成测试 | 乘除、平方根、三角函数的实现错误 |
| V2 | 同一运行时内确定 | 同一份输入回放 N 次，每帧哈希都要一致 | 未初始化状态、随机数、遍历顺序 |
| V3 | **架构守卫** | 扫描 `Sim` 和 `Rollback` 程序集的 IL，出现 `float`/`double`、`System.Random`、`DateTime`、对 `Dictionary`/`HashSet` 的遍历就失败 | AI 或人不小心把不确定的东西写进模拟层 |
| V4 | SyncTest | 每一帧都回滚 k 帧再重模拟，比对校验和 | 保存或读取漏了字段、模拟依赖外部状态 |
| V5 | **回滚等价性模糊测试** | 两个模拟对端在随机的网络条件下对战（延迟 0–200 ms、抖动、10% 丢包、乱序，种子固定），确认帧的哈希必须两端一致，并且等于不联网直接跑的结果；在 CI 里跑上千个种子 | 回滚调度、输入确认、预测纠正的边界错误 |
| V6 | 跨运行时确定 | 同一份回放分别在 .NET、Unity Mono（EditMode）、IL2CPP 桌面版、WebGL（无头浏览器）里跑，比对整份哈希日志 | 平台相关的不确定性 |
| V7 | 性能预算 | 最坏情况（回滚 8 帧 + 保存和读取）在目标机器上低于 2 ms | 回滚导致掉帧 |
| V8 | 浸泡测试 | 机器人对机器人，在恶劣的模拟网络下跑 30 分钟，不能去同步 | 长时间才暴露的问题 |
| V9 | 手感（人工） | 按清单试玩：输入响应、回滚造成的画面跳动、击中反馈 | 自动化测不出的体验 |

每一项新检查都要做反向探针：故意注入不确定性，比如在模拟里读一次系统时间、让保存漏掉一个字段，确认它会变红。

`.ai/verify.sh` 放 V1 的快速子集、V2、V3、V4，以及小规模的 V5，控制在一分钟以内；完整的 V5、V6、V8 放进 CI。

## 质疑

- **最弱的假设：WebSocket（TCP）上跑回滚能接受。** TCP 丢包时会阻塞后面的消息，画面会卡一下。缓解：演示以「本机 + 模拟网络」为主，联网版明确标注；WebRTC 数据通道作为延伸。**如果 S5 实测卡顿明显，这条就要重新评估。**
- **定点乘法的溢出。** Q32.32 相乘需要 128 位的中间结果。.NET Standard 2.1（Unity 用的）没有 64×64→128 的 `Math.BigMul`，要自己拆成高低位来算，而这正是最容易出错的地方。所以 V1 必须和 `BigInteger` 比对，并且覆盖边界值。
- **范围失控。** 最大的风险在玩法和手感调优上。缓解：S2 只做上面列出的机制；手感调优在 S4 结束时给固定的时间盒，超出的部分进待办。
- **表现层把不确定性带回模拟层。** 比如 View 读了 `Time.deltaTime`，再传给模拟。缓解：模拟只接受「帧号 + 输入」；V3 管住程序集边界，接口上只放输入结构体。
- **保存和读取太慢。** 如果状态里有托管对象，每帧保存会产生 GC。缓解：从 S2 开始，状态就全部用值类型和定长数组，整块复制；V7 盯住。
- **自己实现回滚算不算「重复造轮子」？** 对作品集来说，自己实现正是要展示的部分。不过设计完全照 GGPO 和 GGRS 的成熟模型来，参考实现留作对照。如果 S3 超时一倍，就退回到参考 Backdash 的结构。
- **回滚怎么退回**：每个阶段结束都是一个能用的状态；S5 失败时，S4 的本机加模拟网络版本本身就是一个完整的演示。

## 已确认的决策（2026-10-15）

1. **游戏**：1v1 平台擂台，把对手打出平台。
2. **定点数**：自己实现，用 `BigInteger` 和 FixedMathSharp 做对照测试。
3. **联网**：两种都做。S5 做 WebGL + WebSocket 中继；S5b 做桌面版 UDP 点对点，两者共用 `ITransport`。UDP 和 TCP 在丢包下的对比，正好可以验证「最弱的假设」那一条。
4. **仓库**：第一天就公开。
5. **项目名**：暂时保留 `rollback-arena`，发布前再定。

（实施中追加）

- **2026-10-15 S0 骨架与检查体系**：用时约 20 分钟（单个 AI 会话，含独立审查约 5 分钟）。AI 写了全部内容：解决方案（Sim、Rollback 为 netstandard2.1 + C# 9，测试项目为 net9.0 + NUnit）、V3 架构守卫（用 System.Reflection.Metadata 扫 IL，没有新增依赖；21 个故意违规的夹具作为守卫自身的反向探针）、`.ai/verify.sh`、CI、`AGENTS.md`。我写了方案，审批了提交和推送。AI 的错和抓到它的检查：① NUnit 4.6.1 在 SDK 9.0.100 下编译不过，被构建抓到，降级到 4.4.0；② `dotnet test -v q` 吞掉了守卫的失败信息，被反向探针抓到；③ 守卫漏掉了 `System.Numerics` 浮点向量、`HashSet.CopyTo`/`RemoveWhere`、`Hashtable`/`ConcurrentDictionary`，被独立审查子代理实测抓到，已补规则和夹具。
- **2026-10-16 S1 第一步：Fixed64 骨架与 V1 测试（乘法待人实现）**：用时约 30 分钟（单个 AI 会话，含独立审查约 4 分钟）。AI 写了：`Fixed64` 骨架（构造、常量、饱和加减与取负、比较、相等、不用浮点的 `ToString`；`Mul` 抛 `NotImplementedException`）；测试项目里的 BigInteger 参考实现、SplitMix64 固定种子生成器、54 条手算期望值的乘法边界用例（正反两序，共 98 个）；加减与比较的测试（各 100 万组随机用例，绿）；乘法测试 197 个（`HumanTodo`，全部因 `NotImplementedException` 而红）；`verify.sh` 排除 `HumanTodo`。反向探针：朴素版 `Mul`（raw×raw 直接右移 32 位）让 153 个乘法测试变红；去掉 `Add` 的饱和、把参考实现的舍入改成「一半时向 +∞」，都被绿色测试抓到。我做了：选定乘法舍入方式（四舍五入，一半时远离零）和溢出策略（饱和），审批提交；乘法由我接着写。AI 的错和抓到它的检查：① 生成器里「自乘结果在 MaxValue 附近」的常量多写了一位十六进制（成了 √2·2^51），这条覆盖路径因此失效，被独立审查子代理实测抓到，已改正。
